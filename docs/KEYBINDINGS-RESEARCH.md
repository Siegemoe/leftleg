# Keybinding research — 2026-09-20

Cross-tool keybinding conventions for the Leftleg keymap proposal, verified against
official/primary documentation fetched live on 2026-09-20. One section per source
family, then two summary tables: chord ownership on Windows, and conflict-prone
chords.

Reading notes:

- The "Recommended default" column records the default the evidence supports — the
  convention other tools have already trained into Windows users. It is an input to
  the separate keymap proposal, **not** a decision.
- Every row cites the page it was verified against. Where a source could not confirm
  something, the row says so; nothing is filled in from memory. Consolidated
  unconfirmed items are listed at the end.
- Chords are Windows chords unless stated. Citations `[n]` refer to the numbered
  source list at the end.

**Two-stroke chord system.** Chords are two sequential key presses, written
`"ctrl+k ctrl+s"` — "Chords (two separate keypress actions) are described by
separating the two keypresses with a space" [2]. The default map holds 28 distinct
`Ctrl+K …` commands: folding (`Ctrl+K Ctrl+L/0/J/[`/`]`), comments
(`Ctrl+K Ctrl+C/U`), formatting, hover, editor-group arrangement
(`Ctrl+K Ctrl+Left/Right`, `Ctrl+K W`, `Ctrl+K Ctrl+W`), file utilities
(`Ctrl+K S` Save All, `Ctrl+K P` Copy Path, `Ctrl+K R` Reveal, `Ctrl+K Enter`
Keep Open), and display modes (`Ctrl+K Z` Zen, `Ctrl+K Ctrl+T` theme). The docs do
not state a rule for _when_ to chord — that framing is not in official docs — but the
pattern is: secondary/less-frequent commands of one family go under a mnemonic prefix
key. Zed replicates the same prefix with `ctrl-k …`, and Claude Code uses a `Ctrl+X`
prefix with a 3-second chord window (§5).

**Conflict resolution.** "Rules are evaluated from bottom to top. The first rule that
matches both the `key` and `when` clause, is accepted. If a rule is found, no more
rules are processed"; user keybindings.json rules are "appended at runtime to the
bottom of the default rules, thus allowing them to overwrite the default rules" [2].
The commonly quoted "later binding wins" / "most-specific when-clause wins" wording is
**not** in the docs. Removal syntax is `"command": "-workbench.action…"`.

related to editing, navigation, refactoring, debugging, and other tasks"; all defaults
are configurable [mastering page]. Predefined keymaps are read-only; custom keymaps

[configuring page]. JetBrains ships alternative keymaps, but a built-in VS Code keymap
is **not** named on the keymap pages (they name Eclipse/NetBeans); the VS Code keymap

page]. JetBrains' own framing: "Search Everywhere is your replacement for Command

**Customization model.** Keymap is a JSON array of binding groups; each key in
`"bindings"` "is a sequence of keypresses separated with a space… Each keypress is a
sequence of modifiers followed by a key" — chords like `"cmd-k cmd-s"`, `"space e"`,
and modifier-only chords (`"shift shift"`, fired on key release) are supported. With a
conflicting prefix, "Zed will wait for 1 second after you type `ctrl-w`" before firing
the shorter binding. Bindings are active unless a `"context"` is set; contexts form a
tree rooted at `Workspace` with `&&`, `||`, `!`, and ancestor (`X > Y`) expressions.
Shippable base keymaps: Zed (default), VS Code, Atom, Emacs (Beta), JetBrains,
Sublime Text, TextMate, Cursor, None. User keymap on Windows:
`~\AppData\Roaming\Zed\keymap.json`. Sources: https://zed.dev/docs/key-bindings

### Tauri menu accelerators vs webview keydown — the interception claim, verified

**The hypothesis "OS-registered accelerators intercept before the webview sees the
key" is not supported; on Windows the documented evidence is the reverse.** Tauri's
menu guide is silent on the interaction (it only shows accelerator strings like
`Some("Ctrl+Z")` and `setAccelerator('Ctrl+L')`, with no behavior or platform notes
[22]). The mechanism, per first-party sources:

- muda (Tauri's menu crate) documents that "On Windows, accelerators don't work unless
  the win32 message loop calls `TranslateAcceleratorW`" [23].
- wry #451 (open since 2021-12, `upstream`, `priority: high`): menu accelerators fire
  on macOS but not on Windows; maintainer: "the webview hijacks the keyboard events
  from the underlying win32 window procedure" — WebView2 consumes keydown before the
  host's `TranslateAcceleratorW` runs, so the **page's keydown sees the chord and the
  native menu accelerator never fires**. WebView2's `add_AcceleratorKeyPressed` did not
  help; `AllowHostInputProcessing` (WebView2 SDK 1.0.3351.48) is the upstream fix path
  but has focus-management side effects; blocked on WebView2Feedback #468. [24]
- tauri #6365 ("menu accelerator not working on Windows") was closed as a duplicate of
  #4085 ("waiting for microsoft"). [25]
- Community workaround pattern: frontend capture-phase `keydown` listeners that
  dispatch the same handler the menu item declares, on Windows only. [24]
- Separately, WebView2 has its own built-in browser accelerators (e.g. `Ctrl+J`
  opens its Downloads UI, reported to be non-preventable from page JS;
  `Ctrl+R` reload). wry exposes `with_browser_accelerator_keys(bool)` mapping to
  WebView2's `AreBrowserAcceleratorKeysEnabled` (default true) to control that layer.
  [24] [26]

**Practical conclusion for Leftleg (Windows-first):** the webview `keydown` handler is
the authoritative chord layer on Windows; native menu accelerators cannot be relied on
to fire (and therefore cannot pre-empt the page). Menus should mirror actions, with the
shortcut labels declarative, while actual key handling lives in the frontend. macOS
reverses this (native key-equivalents work there), which matters only if a mac build
ever ships. Accelerator grammar is muda's: `Ctrl|Control`, `Alt|Option`, `Shift`,
`Cmd|Super|Meta`, plus `CmdOrCtrl`/`CmdOrControl` aliases (= `Meta` on macOS,
`Control` elsewhere); muda warns accelerators "cannot represent all shortcuts found on
non-U.S. keyboard layouts". [23] OS-wide shortcuts are a separate mechanism
(`global_shortcut` plugin, fires without window focus, needs capability grants). [27]
